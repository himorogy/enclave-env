# 先頭ドットのドメインに解決失敗の警告を出さない

## 内容

0020 の先行検証（publish 前の egress-guard を `devcontainer-base:edge` に焼き、利用側
リポジトリで L7 を立てて実機で確かめた）で出た。**機能は正しく、適用ログの文言だけが誤っている。**

### 何が起きているか

`allowDomains` に先頭ドットの記法（`.example.com`）を書いて L7 で適用すると、次が出る。

```
[firewall] WARNING: failed to resolve .example.com, skipping
```

一方、同じ実行で proxy の ACL には `.example.com` が入っており、`www.example.com` へ実際に
到達できる（先行検証で確認済み）。**つまり許可は成立しているのに、警告は「解決できなかったので
飛ばした」と言っている。**

原因は `add_domain` が全ドメインを DNS 解決することにある。L7 でも解決するのは意図的で、
コード中のコメントのとおり「名前が生きていることの確認（anchor check）」に使うためである。
ところが**先頭ドットの記法は DNS 名ではない**——`example.com` とそのサブドメインを表す
ワイルドカードの綴りであり、その文字列をそのまま問い合わせても答えが返らない。だから必ず
失敗し、必ず警告が出る。

**先頭ドットは 0019 が L7 のために導入した記法である。** L7 の利点として案内している書き方を
使うと毎回警告が出る状態になっており、利用者は許可されていないと誤解する。「skipping」の語も
実態と合っていない（飛ばされていない）。

### このチケットで行うこと

- **先頭ドットで書かれたドメインは DNS 解決の対象から外す。** 解決できないのが正常であり、
  失敗として扱わない。警告も出さない
- **ACL への載せ方は変えない。** `--print-proxy-acl` の出力は 1 行も変わらない
- 適用ログでの扱いを決める。**黙って消さず、その名前が許可に含まれていることが読める形で残す**
  ——利用者が「書いたものが効いているか」を適用ログで確かめられる状態は保つ。文言は実装者が
  決めてよいが、`resolves` のように解決した事実を装う書き方は避ける
- **anchor check への影響を確認する。** 先頭ドットのドメインが anchor に選ばれる経路が
  あるなら、そこでも同じ扱いにする（先頭ドットは生存確認の対象にならない）

### やらないこと

- **L3 側の挙動は 1 行も変えない。** L3 は先頭ドットの記法を設定の検証で拒否する（0019 の
  判断）。このチケットは L7 で受理された後の扱いだけを直す
- **通常のドメインの解決失敗の警告は残す。** `api.example.com` のような DNS 名が引けないのは
  設定の誤りか障害であり、警告に意味がある。消してよいのは「DNS 名ではないものを引こうとして
  失敗した」場合だけ
- 禁止レンジに解決したときの警告（`resolved only to forbidden addresses`）は触らない
- 最終テーブルの構成・ACL の内容・proxy 側の設定は変えない

## 保証

### 新たに宣言する保証

- 設定に書いたドメインを解決できないとき、適用ログにはその名前を挙げた警告が出る。**先頭ドットの
  記法だけはこの対象から外れる**——DNS 名ではないため解決を試みず、解決できなかったことを理由に
  警告することもない。許可としては従来どおり成立し、`--print-proxy-acl` の出力は変わらない
  （テスト: 実装時に確定する。解決できない通常のドメインで警告が出ること、先頭ドットでは出ない
  こと、先頭ドットを含む設定の ACL 出力が変わらないことの 3 点を置く）

### 維持する保証

- 台帳 §4 の設定の検証に関する行——**このチケットは設定の読み取りも検証も変えない。**
  L3 が先頭ドットを拒否する挙動もそのまま
- 台帳 §5 の最終 IPv4 テーブルに関する各行（L3 側・L7 側とも）——テーブルの構成は変わらない。
  変わるのは適用ログの文言だけである
- 0020 が宣言した「L7 では GitHub の meta API を取得しない」ほか、実現層による分岐の各行

### 廃止する保証

- なし。警告が出る条件を正す変更であり、取り下げる約束は無い。解決できないドメインが報告される
  こと自体は**これまで台帳に行を持っていなかった**ので、上の新規宣言は既存の行の書き換えではなく
  追加である
